# 03. 管理画面・障害時挙動・注意点

## 1. 管理画面の設計

### ログイン

- 運営専用URLを参加者画面と分離する。
- パスコードログインのみを採用し、複雑な認証は入れない。
- セッションは httpOnly cookie で保持する。
- 重要操作前は必ず確認ダイアログを出す。

### 運営ダッシュボードで見えるべき情報

1. 卓一覧
   - 卓番号
   - 固定ゲーム名
   - 状態
   - 使用中参加者
2. 待機中参加者
   - ニックネーム
   - 待機秒数
   - 運営戦候補か
3. 対戦中試合
   - 卓番号
   - 対戦者
   - 状態
   - 開始時刻
4. 接続切れ参加者
   - ニックネーム
   - 切断前状態
   - 最終通信時刻
5. 要介入試合
   - 勝利申告中で長時間停滞
   - 承認拒否が発生した試合
   - `matches.dispute_count > 0` の試合

### 参加者管理画面

各参加者に対して以下を実行できる。

1. チップ修正
2. 一時停止
3. 一時停止解除
4. 失格
5. 失格解除はMVP外でもよいが、DB上は戻せる形にする
6. 現在状態と current_match_id の確認
7. 一覧取得は server-side read service で行い、mutation API と混ぜない

### 試合管理画面

1. 勝敗修正
2. 試合無効化
3. 強制終了
4. 関連する卓の解放
5. 双方参加者状態の復旧
6. 一覧取得は server-side read service で行う

### 卓管理画面

1. 卓強制解放
   - 関連 match の無効化と参加者状態復旧を含む
   - RPC: `force_release_table`
2. `admin_hold` への切り替え
   - 空き卓を `admin_hold` にし、新規マッチング対象から除外する
   - `reserved` / `in_use` の卓は先に match を解決してから hold する
   - RPC: `hold_table_by_admin`
3. `admin_hold` の解除
   - `admin_hold` → `available` に戻し、マッチング対象に復帰させる
   - RPC: `release_table_admin_hold`
4. 現在の match 表示
5. 強制解放時の副作用確認（対象 match / participant の状態変化を表示）
6. 一覧取得は server-side read service で行う

### 運営戦開始画面

1. 待機者一覧から対象を選ぶ
2. 空き卓を自動選択
3. 必要なら卓指定
4. 対戦成立後は参加者側では通常マッチに近い表示を出すが、結果確定は運営側が行う

## 2. 例外ケース一覧

最低限、以下を例外ケースとして設計・テスト対象にする。

1. 同じニックネームで参加しようとした
2. 会場コードが違う
3. 新端末ログインで旧セッションが残っている
4. 待機中に切断した
5. マッチ成立直後に片方が切断した
6. 開始ボタンを片方だけ押したまま止まった
7. 開始前キャンセルと相手の開始押下が競合した
8. 双方がほぼ同時に開始を押した
9. 勝利申告を双方がほぼ同時に押した
10. 勝利申告後に相手が切断した
11. 承認拒否後に再度勝利申告した
12. 結果確定と運営修正が競合した
13. 対戦中に失格処理した
14. 卓が埋まっていてマッチングだけ進みそうになった
15. 運営戦候補だが空き運営がいない
16. チップが0の参加者が待機開始した
17. 所持チップがベット額未満で開始した
18. 運営戦で参加者が勝利した
19. 再接続時に state と current_match_id が不整合
20. ランキング取得時に失格者が混在する
21. 運営戦で参加者が ready を押したが、運営が結果確定前に卓解放しようとした
22. 一時停止解除後に再度待機へ戻れるか

## 3. 例外処理・障害時挙動

### 参加登録

- ニックネーム重複: 409 で返し、入力欄下にエラー表示
- 会場コード不正: 401 or 400 で返し、再入力させる
- 旧セッション存在: 旧セッションを無効化して新規発行

### マッチング

- 空き卓なし: 待機継続
- 対人候補なし: 待機継続
- 運営戦候補化済みだが運営不在: 待機継続
- マッチング確定中に競合: RPC 内の transaction で再試行または失敗復帰
- チップが 0 以下: 待機開始を 409 で拒否し、ホームで運営へ相談させる

### 試合開始

- 相手不在で ready: `awaiting_ready` のまま
- 相手が先にキャンセル: エラーではなく状態再取得して `registered` に戻す
- チップ計算競合: サーバー側再計算を正とし、クライアント入力値は信用しない

### 対戦中

- 勝利申告競合: 先勝ち1件だけ受理し、後発は 409 で現在状態を返す
- 承認拒否: 試合を `in_progress` に戻し、`dispute_count += 1`, `last_disputed_at = now()` を記録する
- 参加者切断: 試合は自動終了しない。運営介入可能にする
- 運営戦: 参加者側の勝利申告 / 承認は使わず、運営が結果確定する

### 結果確定

- ledger 書き込み失敗: transaction 全体を rollback
- 二重確定防止: `matches.status='winner_claimed'` を条件に更新

### 運営修正

- 重要操作は確認ダイアログ
- 実行後は対象 participant / match / table をまとめて再取得
- 可能なら `admin_audit_logs` に記録。MVP未実装でも service 層のフックは用意する
- 一時停止解除は `paused -> registered` への明示操作として用意する

## 4. 接続切れ時の扱い

### 切断判定

- `last_seen_at` がイベント設定の閾値を超えたら切断扱い
- バッチまたは定期ジョブは不要。heartbeat 時、管理画面表示時、マッチング処理時に都度判定してもよい

### 切断中にやらないこと

- 自動敗北
- 自動ベット返金
- 自動運営呼び出し

### 再接続時

- セッションが有効なら current state に戻す
- 無効なら再ログインさせる
- 旧セッションからの操作は 401 を返す

## 5. 危険な点・注意点

### 実装上の危険

1. 状態更新をクライアント主導にすると破綻しやすい
2. マッチ成立、開始、結果確定でアプリ層から複数クエリを順番に流すと不整合が起きやすい
3. `participants.status` だけで進行を持つと match / table とずれやすい
4. 同時押下系を idempotent にしないと二重反映が起きる
5. Realtime は Broadcast invalidation に責務を絞り、認可済み read API 再取得と組み合わせて複雑化を抑える

### 運用上の危険

1. 会場Wi-Fi不安定時に切断表示が増える
2. 現物チップとアプリ残高がズレても、正式記録はアプリ側だと参加者に明示が必要
3. 勝敗申告が自己申告ベースなので、揉めた時に運営が直せる導線が必須
4. 卓に移動しない参加者がいると回転が落ちる
5. 初期チップが少なすぎる / 多すぎるとゲーム回転数が大きく変わるため、イベント設定で調整可能にする

### MVPとしての割り切り

1. 自動救済や自動仲裁は入れない
2. 詳細な監査画面は後回し
3. 切断復帰は「状態復元できる」ことを優先し、「完全自動回復」は狙わない
4. 画面同期は Realtime Broadcast を標準とし、運営画面でも常時 periodic polling に依存しない（Realtime 断時のみ `30秒` フォールバック polling を許可）
