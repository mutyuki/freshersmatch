# 00. 要件整理とMVP定義

## 1. 要件の要約

- 教室内イベントで使う、参加者向けスマホ中心のWebアプリを作る。
- アプリの責務は「参加登録」「マッチング」「卓割当」「チップ正式記録」「結果反映」「ランキング表示」。
- 実際のゲーム進行は卓上の実物カードやチップで行い、アプリ内でゲームロジックは実装しない。
- 参加者は QR コードから参加ページへ入り、会場コードと一意なニックネームで参加する。
- 参加者は「マッチング開始」で待機し、原則として対人戦を優先してランダムマッチングされる。
- 直前に戦った相手は可能なら避けるが、候補不足時は無視してよい。
- 一定時間待機した参加者は運営戦候補にできる。運営戦が成立したらそのマッチは確定で差し替えない。
- 卓は5卓固定で、空き卓を割り当てる。卓ごとのゲーム内容は固定。
- 試合は双方が開始ボタンを押した時点で開始し、その時点でベットを差し引く。
- ベット額は固定値で、所持チップ不足時はオールイン。少ない方に合わせ、サイドポットはなし。
- 開始前のみキャンセル可能。キャンセル時はチップ増減なし、卓は解放される。
- 勝者申告後、敗者が承認したら結果確定し、チップ・ランキング・卓状態を更新する。
- 承認拒否時は対戦中へ戻し、必要に応じて運営が後から修正できる。
- 30秒以上通信断で切断扱いにするが、MVPでは過剰な自動救済は実装しない。再接続復帰を優先する。
- 運営画面は一般参加者画面と分離し、卓強制解放・勝敗修正・チップ修正・一時停止・失格・運営戦開始を行える。
- ランキングは総チップ所持数順。モニター用のシンプルな閲覧画面があると望ましい。

## 2. 補完した前提

要件の意図を崩さない範囲で、以下を設計前提として補完する。

1. 会場コードはイベント単位で1つ発行し、参加者登録時に照合する。
2. 1ユーザー1セッションは「参加者レコードに現在有効なセッショントークンIDを1つだけ持つ」方式で実現する。
3. 再読み込み復帰は「セッショントークン + 現在の participant_state / current_match_id を読んで復元する」方式とする。
4. 卓の「仮予約」は、マッチ確定から試合解消または開始までの短い占有状態を指す。
5. 運営戦は「運営アカウント自身が卓に入る」のではなく、「運営側の仮想対戦相手レコード」を使わず、match に `is_staff_match=true` と `staff_operator_id` を持たせる方式とする。チップ記録は参加者側の増減のみ。
6. 同順位は `chip_balance DESC, updated_at ASC, participant_id ASC` の順で安定ソートする。表示上は同チップなら同順位でもよいが、MVP実装は単純な順位番号表示でもよい。
7. 30秒切断判定はリアルタイム接続のハートビートではなく、`last_seen_at` のサーバー更新時刻で判定する。
8. マッチングは厳密な常時自動探索ではなく、「待機キュー変更時にサーバーが都度再計算する」方式で十分とする。
9. 0チップ救済はMVP対象外とし、DB拡張しやすい位置だけ残す。

## 3. MVPの範囲

### MVPに含める

- 参加者登録
- 一意ニックネーム制御
- 単一セッション制御
- 参加者の現在状態復元
- 対人優先ランダムマッチング
- 直前対戦相手の回避
- 待機超過時の運営戦候補化
- 卓割当
- 開始前キャンセル
- 双方開始で試合開始
- 固定ベット / オールイン処理
- 勝者申告 / 敗者承認
- 結果確定とチップ反映
- ランキング一覧
- 運営画面ログイン
- 卓強制解放
- 勝敗修正
- チップ修正
- 一時停止 / 失格
- 運営戦の手動開始
- リアルタイム更新
- 再接続復帰

### MVPから外す

- 0チップ救済の本実装
- 詳細な監査ログUI
- 自動通報フロー
- 複雑な通知設計
- 高度な不正検知
- 複数イベント並行運用の汎化
- きめ細かい分析ダッシュボード

## 4. 画面一覧

## 4.5 レイアウト前提

### 参加者向け画面

- スマホファーストで設計する。
- 想定幅は `320px-430px` 程度の縦持ちを優先する。
- 1画面1目的を徹底し、同時に複数操作を並べすぎない。
- 主要操作ボタンは画面下部寄りに大きく配置する。
- 参加者は移動しながら使うため、情報は「現在状態」「卓番号」「相手」「押すべきボタン」に絞る。
- ランキングもスマホで読める縦一覧を基本にする。

### 運営向け画面

- PCブラウザ前提で設計する。
- 想定幅は `1280px` 以上を優先し、一覧性を重視する。
- 卓一覧、待機者一覧、対戦中一覧を同時に見られるダッシュボードを基本にする。
- 重要操作はテーブル行アクションまたは詳細モーダルから実行する。
- スマホ運営UIはMVP対象外とし、最低限のレスポンシブ対応に留める。

### 参加者向け

1. 参加登録画面
   - 会場コード入力
   - ニックネーム入力
   - 参加確定
2. 参加者ホーム画面
   - 現在状態表示
   - 所持チップ表示
   - マッチング開始ボタン
   - ランキング導線
3. マッチ待機画面
   - 待機中表示
   - 待機時間表示
   - 待機解除ボタン
4. マッチ成立画面
   - 対戦相手ニックネーム
   - 卓番号

   - 開始ボタン
   - キャンセルボタン
   - 相手の準備状態
5. 対戦中画面
   - 卓番号
   - 対戦相手
   - ベット額 / 実際に賭けた額
   - 勝利申告ボタン

## 5. 主要ユーザーフロー

### 参加者登録から初回対戦まで

1. QRコード読み取り
2. 参加登録画面表示
3. 会場コード入力
4. ニックネーム入力
5. サーバーで会場コードとニックネーム一意性を検証
6. 参加者セッションを発行
7. ホーム画面へ遷移
8. 「マッチング開始」を押す
9. 待機キューへ追加
10. マッチ成立時に卓番号・対戦相手・ゲーム名を表示
11. 双方が開始ボタンを押す
12. ベット差し引き後、対戦中状態へ遷移

### 結果確定フロー

1. 勝者が「勝ちました」を押す
2. 試合状態を `winner_claimed` に更新
3. 相手へ承認ダイアログを表示
4. 相手が承認したら結果確定
5. チップ残高更新
6. 卓解放
7. 両者を `registered` 状態に戻す
8. ランキングを更新表示

### 承認拒否フロー

1. 敗者が「承認しない」を押す
2. 試合状態を `in_progress` に戻す
3. 勝利申告フラグをクリア
4. 参加者はそのまま対戦中画面へ戻る
5. 運営は必要に応じて試合管理画面から介入する

### キャンセルフロー

1. マッチ成立後、開始前にどちらかがキャンセル
2. 試合を `cancelled_before_start` にする
3. 卓を解放
4. 両参加者を `registered` に戻す
5. チップ変動なし

## 6. この仕様でまず作るべき最初の3機能

1. 参加登録と単一セッション復帰機能
2. 待機キューからのマッチングと卓割当機能
3. 試合開始から勝敗確定までの状態遷移とチップ反映機能
